1The problem with a free canvas

qpwgraph's canvas is a plain QGraphicsScene: every node is a freestanding item you drop wherever, and it stays exactly there until you drag it again. There is no notion of "this belongs on the left" — the layout you end up with is just the accumulated history of everywhere you've ever dropped something. New nodes appear at a default spawn point and pile up; tiles overlap; cables cross wherever the geometry happens to put them.

The one thing already fighting this is a local patch (0003-Add-auto-arrange-nodes-button-to-toolbar.patch): a toolbar button that sorts every visible node into three columns by nodeMode() — sources left, duplex/none centre, sinks right — and restacks each column top-down. It's a one-shot snapshot, not a standing layout: run it once, then drag things back into a pile. The idea below turns that one-shot sort into the permanent shape of the window, plus a fourth column for whatever isn't part of the working setup right now.

2Four zones, not one canvas

Three vertical zones span most of the window, plus one horizontal zone along the bottom:

Inputs — left

Anything feeding audio (or MIDI, or video) into the graph: microphones, line-in, capture devices, and playback applications like a browser or media player, since from the graph's point of view they're a source too.

Middle — centre

Everything that both takes input and produces output: EasyEffects' sink and source nodes, loopbacks, Carla, a virtual mixer. This is the working area — routing and DSP live here.

Outputs — right

Where audio ultimately lands: hardware playback devices, HDMI audio, a recorder or streaming app's input.

Unused — bottom

A shelf for whatever isn't part of the current working setup: a disconnected interface, a MIDI controller, a webcam. Out of the way, but one drag from being back in play.

Terminology trap

qpwgraph's own qpwgraph_item::Mode enum (qpwgraph_item.h) names a node by which ports it exposes, not by what a user calls the device: Output means "has only outgoing ports" — a microphone, a media player — and Input means "has only incoming ports" — a speaker. That's the exact inverse of the zone names proposed here. The existing autoArrangeNodes() already made this call correctly (nodeMode() == Output → left column), so the mapping isn't new, but it's worth a code comment where it happens, because it reads backwards on a first pass.

audio port MIDI port video port other port — qpwgraph's own default port-type colours (qpwgraph_pipewire::resetPortTypeColors()), reused here rather than invented.

3How a node picks its zone

A default falls out of what qpwgraph_pipewire already knows about a node the moment it appears — no new PipeWire-side data needed. A manual drag always overrides the default, and that override sticks.

4Moving a tile between zones

Dragging a tile out of one zone and into another is the entire "select what you're using" workflow the request asks for — plug in an interface, it lands in Unused because nothing's connected yet, drag it up into Inputs the moment you start using it.

5Stacking without overlap

Within a zone, tiles behave like a vertical shelf-packer, not free-floating items: fixed horizontal position, stacked top-to-bottom with a constant gap, ordered by whatever the last drag or alphabetical default left them in. Inserting a tile anywhere but the bottom pushes everything below it down by exactly its height plus one gap — nothing ever needs to overlap, because there's no free coordinate to overlap into.

6Collapsing long stacks

Figure 4 stops a stack from overlapping, but it doesn't stop a stack from getting long — and one real-world case makes it long fast. Turning on EasyEffects for a single device doesn't add one node to the Middle column, it adds one node per plugin in the chain, because EasyEffects builds its filter graph out of individually-addressable PipeWire nodes and tags them with a shared node.group property (PW_KEY_NODE_GROUP, set to ee_sink_group / ee_source_group in EasyEffects' own pw_node_manager.cpp) precisely so other tools can tell they're one unit. qpwgraph doesn't read that property today — its node-info callback (qpwgraph_pipewire.cpp, around the PW_KEY_NODE_DESCRIPTION/PW_KEY_NODE_NICK lookups) only pulls name, nick, description and id — so all of it lands as separate tiles.

A second, unrelated case produces the same clutter for a different reason: some nodes exist purely to expose a control, not to carry a signal anywhere. pwvucontrol-peak-detect — spawned by pwvucontrol itself whenever a level meter is open — is a real example already living on this machine; GNOME's volume-key handler (gsd-media-keys) and its on-screen-display helper (org.gnome.VolumeControl) are two more. None of them has a meaningful position in a signal-flow diagram, and tellingly, EasyEffects already hard-codes this exact set of names into a blocklist (blocklist_node_name, pw_node_manager.hpp) rather than let its own graph view show them.

Two separate mechanisms follow from that, and they resolve before Figure 2's zone classification ever runs:

Group into one tile

Nodes sharing a node.group collapse into a single tile the size of any other, labelled with the group's anchor node (the sink or source, not a plugin) and a small "+N" disclosure. Expanding it reveals the members inline, pushing the rest of the stack down exactly as Figure 4 already does for a plain insert — collapsing is just that in reverse. Where node.group is absent (not every app sets it), a name-prefix fallback catches the common case, but is a heuristic, not a guarantee — see §9.

Fold or hide control-only nodes

A node matched against a small blocklist — starting from EasyEffects' own list plus media.role=event — never gets a tile of its own. Best case, it's attached as a small icon (a peak-meter glyph, a mute badge) to the tile of the node it actually controls; failing an obvious pairing, it's simply not drawn. Either way it never occupies a slot in Unused, which is for things you might use, not for plumbing nothing points at.

7What this means for the codebase

The node and port classes already carry everything a zone assignment needs — qpwgraph_item::Mode and the four port-type accessors on qpwgraph_pipewire (audioPortType(), midiPortType(), videoPortType(), otherPortType()) are exactly the classify() inputs in Figure 2. What doesn't exist yet is a managed layout to place them in — qpwgraph_canvas is a bare QGraphicsScene/QGraphicsView, and autoArrangeNodes() (the existing patch) works by computing absolute x,y once and calling node->setPos(). That's a snapshot, not a constraint — nothing stops the next drag from breaking it again.

The zoned model wants that to be a standing constraint instead of a one-shot layout pass. Qt already has the mechanism: qpwgraph_node is a QGraphicsPathItem; wrapping each zone's contents in a QGraphicsWidget managed by a QGraphicsLinearLayout (vertical) turns "stack without overlap" into something the layout engine does for free on every add, remove, or resize — no manual y bookkeeping at all. Four such widgets — three side by side for Inputs/Middle/Outputs, one full-width beneath for Unused — replace today's single unconstrained scene. Reassigning a node's zone becomes layoutA->removeItem(node); layoutB->addItem(node); plus updating the persisted zone key; the layout reflows both sides automatically. QGraphicsSplitter-style drag handles between the three columns give the resizable dividers in Figure 1 without extra plumbing. A collapsed group (§6) is just one more widget in that same layout — its member nodes live in a child layout inside it that only participates in the parent's size when expanded.

Grouping and folding both need one thing qpwgraph doesn't currently fetch at all: the node-info callback in qpwgraph_pipewire.cpp reads PW_KEY_NODE_DESCRIPTION, PW_KEY_NODE_NICK, PW_KEY_NODE_NAME and PW_KEY_NODE_ID, and nothing else — PW_KEY_NODE_GROUP, PW_KEY_MEDIA_ROLE and PW_KEY_APP_ID aren't looked up anywhere in the tree. That's new plumbing before it's a UI change: pull those three properties through alongside the existing ones, store them on qpwgraph_node, and the group-by/fold-by logic in §6 has something to match against.

Persistence — already there, just needs a sibling

Corrected from an earlier draft of this doc: node position is already durably stored — qpwgraph_canvas::saveNode()/restoreNode() write and read a QPointF per node under the GraphNodePos QSettings group, keyed by nodeKey() (node name, plus mode for split Input/Output nodes of the same name). It runs automatically on every addItem()/removeItem(), which is exactly why the freeform canvas already "remembers" where you dropped something between runs even though it feels unmanaged — position persists, but nothing about grouping or intent does. Zone + order-within-zone is a natural sibling group (GraphNodeZone, say) keyed the same way, not a new file. Group-expanded/collapsed state and any manual fold override belong there too.

9Open questions

  • Mixed-type nodes. A node that exposes both audio and MIDI ports (some virtual instruments do) doesn't have a clean single zone under the Figure 2 rule as written — probably fine to classify by port count majority and let a manual drag settle it, but worth deciding before Phase 0 rather than during.
  • Very long stacks. A zone with more tiles than fit on screen needs its own scrollbar once QGraphicsLinearLayout is doing the stacking — should be close to free with QGraphicsWidget, but not yet verified.
  • Cable rendering across zone boundaries. Figure 1's clean gutter routing assumes cables only ever run Inputs→Middle→Outputs left-to-right. A cable from Unused into an active zone (before the tile itself is dragged there) is a real case — e.g. quickly patching a still-parked device — and needs a routing rule of its own.
  • Grouping without node.group. Not every app tags its helper nodes the way EasyEffects does — Carla's internal plugin nodes, for instance, may need a name-prefix or app.id-based fallback instead. A fallback heuristic will occasionally group (or fail to group) the wrong things; it needs to be easy to override per node, the same way a manual zone drag already is.
  • Folding needs a target to fold onto. The peak-detect example works because its name says what device it's metering closely enough to guess. A control-only node with no such hint has nothing obvious to attach itself to — those should probably just be hidden outright rather than guessed at.
